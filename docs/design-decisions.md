# 設計の判断と理由

**この文書の読み手:** 「なぜ、そう作ったのか」を知りたい開発者と、新しい会話の AI エージェント。検証の計画は [plan.md](plan.md)、判断の根拠になった事実は [findings.md](findings.md)。用語は [用語集](glossary.md)。

新しい判断は、末尾に足す。判断は 1 行に 1 つ。影響には、悪い面も書く。状態は「提案」「承認」「廃止」のいずれかにする。最初の 15 行は、第 1 部（内部の mTLS の基盤）で決め、第 2 部でも使い続ける判断である。

| 判断 | 理由 | 退けた案 | 影響 | 状態 |
|---|---|---|---|---|
| アプリ（Node.js）が自分で mTLS を終える。Envoy などのサイドカーを前に置かない | ECS の bridge モードでは、同じタスクのコンテナもネットワークを共有しない。サイドカーの後ろのアプリにも直接届き、サイドカーが付けるヘッダー（`x-forwarded-client-cert`）を偽れる | Envoy のサイドカー（gekko_11 の方式。Kubernetes の Pod はネットワークを共有するので成り立った）。awsvpc モードでタスクのネットワークを共有する（t4g.small は ENI が 3 つまでで、タスクが足りない） | 良い: 迂回の経路がない。悪い: mTLS の扱いを、各アプリの言語で書く | 承認 |
| ECS のネットワークモードは bridge にする | 上の行のとおり、アプリが mTLS を終えるので、直接届いても証明書がなければ拒める。ENI の数に縛られない | awsvpc（ENI の数で、タスクの数が限られる）。host（全コンテナがホストのネットワークを共有し、ポートが衝突する） | 良い: 1 台に全タスクを載せられる。悪い: タスクどうしは docker のブリッジでつながり、ネットワークでは分けられない | 承認 |
| SVID は spiffe-helper のサイドカーがファイルに書き、アプリは読むだけにする。アプリには agent のソケットを渡さない | 登録のセレクターを「ファミリー」と「コンテナ名 `svid-helper`」の組にでき、アプリのコンテナ自体は身元を取りに行けない | アプリが SPIFFE の Workload API を直接呼ぶ（Node.js の公式のライブラリがない） | 良い: アプリの依存が増えない。悪い: タスクのコンテナが 2 つになる。入れ替えは、アプリが 2 秒ごとにファイルを読んで気づく | 承認 |
| ワークロードは docker の attestor で、ECS が付けるラベル（`com.amazonaws.ecs.task-definition-family` と `com.amazonaws.ecs.container-name`）で見分ける | ECS には SPIRE の専用の attestor がない。ラベルは ECS のエージェントが付け、ローカルでも同じ名前で付けられる | タスクの ARN（タスクごとに変わり、登録を先に作れない） | 良い: 登録をローカルと AWS で同じにできる。悪い: ホストで docker を操作できる者は、ラベルを偽って身元を得られる（[1-3](findings.md#1-3-ラベルを偽ったコンテナにも-svid-が出る)） | 承認 |
| 外への呼び出しは、リクエストごとに接続をつなぎ直す | 接続を使い回すと、入れ替わる前の証明書で示し続ける（gekko_11 の実測 F-G54） | 接続の使い回し（速いが、入れ替えの直後に食い違う） | 良い: 呼び出しは、いつもそのときの SVID で示す。悪い: リクエストごとに TLS の握手が増える | 承認 |
| 実行基盤は ECS の EC2 で、インスタンスはキャパシティプロバイダー（Auto Scaling グループ、0〜上限の台数）のマネージドスケーリングに決めさせる。どの作りも、インスタンスの数と AZ を前提にしない | タスクを 0 にするとインスタンスも 0 になり、使わない間の EC2 と EBS の費用が止まる。インスタンスを増やしても、AZ をまたいでも、作りを変えずに済む | EC2 を直に 1 台作る（1 台を前提にした作りが、2 台目で壊れる。止めても EBS の費用が残る）。EKS（コントロールプレーンの固定費）。Fargate（docker の attestor が使えない。推定） | 良い: 0 台にでき、段 B（マルチ AZ、複数タスク）にパラメーターだけで移れる。悪い: マネージドスケーリングのアラーム 2 つの固定費が出る。縮小は 15 分待つ。0 台から起動すると 2 台を起動した（[3-1](findings.md#3-1-agent-の-daemon-だけが残ったインスタンスをマネージドスケーリングは空として縮めた)、[3-2](findings.md#3-2-0-台から起動するときマネージドスケーリングは-2-台を起動した)） | 承認 |
| アプリどうしは、ECS Service Connect で呼ぶ。使うのは TCP の中継だけで、Service Connect の TLS は使わない | ECS の標準の仕組みで、複数のタスクと AZ への振り分け、タスクの入れ替えを任せられる。Envoy は TCP をそのままリバースプロキシし、mTLS はアプリどうしで端から端まで張る。アプリは Envoy から何も受け取らないので、「サイドカーを前に置かない」の行の理由（サイドカーの付けるヘッダーを信じる）には当たらない | docker0 の IP と固定のホストポート（1 台が前提）。アプリが Cloud Map の SRV を引く（振り分けと引き直しを自前で書く）。Service Connect の TLS（AWS Private CA の固定費。SPIFFE と役割が重なる） | 良い: 呼び出しのコードは名前（`https://ledger:8443`）を呼ぶだけ。悪い: タスクごとに Envoy のコンテナが増え、メモリを使う。プライベート DNS 名前空間のホストゾーンの固定費が出る | 承認 |
| SPIRE server だけを awsvpc モードで動かし、agent は Cloud Map の A レコードの名前で server に届く | agent は IMDS に届くよう、ホストのネットワークで動く。Service Connect はホストのネットワークのモードに対応しない。bridge と host のモードは、Cloud Map で SRV しか作れない（推定） | agent も Service Connect に入れる（モードが対応しない）。内部の NLB（固定費）。server をホストのネットワークに置き、127.0.0.1 で呼ぶ（server のいないインスタンスの agent が届かない） | 良い: server がどのインスタンスにいても届く。悪い: server のタスクは ENI を 1 つ使う（t4g.small は 3 つまで）。EC2 の API へは、タスクの IPv6 で出る | 承認 |
| SPIRE server のデータストア（sqlite）と鍵を EFS に置く。server は 1 タスクに固定する | インスタンスが入れ替わっても、ECS のスタックを作り直しても、CA と登録が残る（[3-3](findings.md#3-3-インスタンスを-0-にして再起動してもefs-の上の-spire-の-ca-と登録は残った)）。EFS は保存した容量の分だけで、固定費がない | ホストのディスク（インスタンスの入れ替えで CA が変わる）。server を複数にして、RDB を 1 つ共有する（RDB が止まれば全体が止まるので、可用性は server 1 つと変わらない。上がるのは server の側の障害だけ）。server 複数と RDB の冗長（Aurora のライターと、別の AZ のリーダー。動いている間の費用が増える。[3-7](findings.md#3-7-aurora-serverless-v2-は-0-acu-まで縮みつながりが-1-本でもあると止まらない)）。ECS の上に PostgreSQL を 1 つ置く（止まると全体が止まる場所が、server から PostgreSQL に移るだけ）。DynamoDB（SPIRE が対応しない。[3-6](findings.md#3-6-spire-server-を冗長にするには全部の-server-が-1-つの-sql-のデータストアを共有するdynamodb-は使えない)）。sqlite を 2 つの server で共有する（資料が本番に勧めず、ネットワークのファイルシステムの上ではロックが当てにならない。推定） | 良い: CA と登録がインスタンスの寿命から切り離される。悪い: server は 1 つなので、5 分ほど止まると、どのインスタンスの agent もワークロードも身元を保てない（[3-4](findings.md#3-4-server-が-5-分ほどいないとagent-は自分の-svid-が切れて止まった)）。EFS は network のスタックにあり、消すと CA も変わる | 承認 |
| 登録とバンドルは、server のタスクの中の registrar のコンテナが作る。バンドルは EFS に書き、agent は最初にそれを信じる | 登録の手順を、インスタンスの数と配置から切り離す。registrar は何度動かしても同じ結果になり、CA が入れ替わればバンドルを書き直す | 各ホストの起動の手順で、同じインスタンスの server に `docker exec` する（server のいないインスタンスで止まる）。SSM のパラメーターでバンドルを配る（ホストに CLI と権限が要る）。agent の `insecure_bootstrap`（最初の接続で server を確かめない） | 良い: どのインスタンスの agent も、同じ手順で server を信じられる。悪い: アプリのイメージに spire-server の CLI（約 160 MB）を入れたので、イメージが大きい | 承認 |
| インスタンスは公開 IPv4 も NAT も持たず、IPv6 だけで外へ出る。AWS の名前は、IPv6 で届くデュアルスタックのものに向ける | 固定費と、インスタンスごと 1 時間ごとの費用を出さない。既定の名前は IPv4 だけだった（[2-3](findings.md#2-3-既定の-aws-の名前は-ipv4-だけでデュアルスタックの名前に向けると公開-ipv4-なしで動いた)） | 公開 IPv4（インスタンスごと 1 時間ごとの費用）。NAT ゲートウェイと VPC エンドポイント（固定費） | 良い: インスタンスが 0 なら、ネットワークの費用も 0。悪い: 向け先の設定が、ECS のエージェント、docker のデーモン、イメージの URI、SPIRE server の 4 か所に散る。Session Manager で入れるかは未確認 | 承認 |
| 各サービスの SVID は、タスク専用のボリュームに書き、同じタスクの app だけが読む | ホストのパスを使わないので、1 台に同じサービスのタスクが 2 つあっても重ならない | ホストのパスに書き、distinctInstance で同じサービスを別のインスタンスに置く（インスタンスの数がタスクの数に縛られる） | 良い: 配置の制約が要らない。悪い: ホストからは SVID を読めない。プローブは、自分のタスクで SVID を得る（次の行） | 承認 |
| `aws/scale.sh down` は、DAEMON 以外のタスクが 0 になったら、ASG の希望台数を直接 0 にする | マネージドスケーリングの縮小は、アラームが 15 分待ち、1 台ずつ縮める。タスクが 0 なら、直接 0 にしても巻き込むタスクがない | マネージドスケーリングに任せる（0 台まで約 18 分かかった）。アラームの条件を書き換える（ECS が作り直すと戻る。推定） | 良い: 数分で 0 台になる。悪い: インスタンスの数を、マネージドスケーリングの外から 1 か所だけ触る | 承認 |
| CloudFormation のテンプレートの Description と Metadata は英語で書く。日本語の理由は `#` のコメントに置き、`scripts/check-templates.sh` がコメント以外の ASCII 以外の文字を止める | CloudFormation は、ASCII 以外の文字を「?」に置き換える（[2-1](findings.md#2-1-cloudformation-はテンプレートの-ascii-以外の文字をに置き換えた)） | 日本語のまま書く（AWS の上で読めない） | 良い: コンソールと AWS の上の注記を読める。悪い: 理由が、英語の要約と日本語のコメントの 2 か所に分かれる | 承認 |
| SPIRE server は 1 つのまま、止まったら速く再起動することで耐える。冗長にするかと、アプリのデータベースを何にするかは、段 B の B-4 の結果を見て一緒に決める | 本当に冗長にするには、server を複数にし、RDB も冗長にする必要があり、動いている間の費用が増える。アプリが RDB を使うなら、SPIRE と相乗りして費用を分けられる。アプリが DynamoDB なら、SPIRE のためだけに RDB が要る | 今すぐ Aurora で冗長にする（B-4 の結果しだいで要らない）。ECS の上の PostgreSQL（止まると全体が止まる場所が移るだけ） | 良い: 固定費を増やさずに進められる。B-4 で、別の AZ へ移したとき server がいなかったのは 24 秒で、連鎖の失敗は 0 件だった（[3-5](findings.md#3-5-spire-server-を別の-az-へ移すとserver-は-24-秒いなかったが連鎖の失敗は-0-件でca-も変わらなかった)）。悪い: 確かめたのは、計画して止め、移し先にインスタンスがあった場合だけ。AZ がまるごと落ちてインスタンスを起動するところから始まると、再起動が SVID の有効期限（5 分）を超えるおそれがある。耐える時間を延ばすには SVID の有効期限を延ばすが、盗まれた鍵が使える時間も延びる。AZ がまるごと落ちた場合の扱いは、アプリのデータベースを決めるときに見直す | 承認 |
