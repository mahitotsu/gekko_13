# ECS on EC2 と SPIRE で、台の数と AZ に依らず、内部の通信を SPIFFE の mTLS で安く守れる

BFF → transfer → ledger の連鎖に、同じシナリオを当てて確かめた。環境は、ローカルの docker、AWS の 1 つの AZ（段 A）、2 つの AZ に各 2 タスク（段 B）の 3 つ。

**この文書の読み手:** この検証の持ち主と、次の題材を設計する開発者、新しい会話の AI エージェント。AWS と OAuth の基礎は知っているが、SPIFFE と SPIRE は知らないことがある。読むと、この作りを採れるか、どこまでが確かめられ、目的に対して何が足りないかが分かる。用語は [用語集](../glossary.md) にある。

**仮置き:** これは第 1 部（内部の mTLS の基盤）の文書で、第 2 部が完成したら消す。第 2 部で要る事実と判断は、第 2 部の文書へ移す。

## 要旨
- **調べたこと:** ECS on EC2 の上で、SPIRE がタスクごとに身元を配り、受け取る側が mTLS の相手とトークンの呼び出し元を照合できるか。台の数と AZ に依らずに成り立つか。
- **身元と付け替え:** 身元は、AWS の識別ドキュメントと ECS のラベルで、当事者の申告に依らずに確かめられた。乗っ取られたタスクが他人のトークンを使うのは、受け取る側が拒めた（[2-1](#2-1-身元は当事者の申告に依らずaws-と-ecs-が付けた印で確かめられる)、[2-2](#2-2-受け取る側はmtls-の相手とトークンの呼び出し元を照合しトークンの付け替えを拒める)）。
- **続けて動くか:** 証明書を 5 分ごとに入れ替えても、2 つの AZ をまたいでも、SPIRE server を別の AZ へ移しても、通信は切れなかった（[2-3](#2-3-証明書の入れ替えazserver-の移動のどれでも通信は切れない)）。台を 0 にすれば、費用は月 1 ドル未満の固定費だけになる（推定）。
- **信頼できる範囲:** 確かめた server の入れ替えは、計画して止めたものだけ。AZ がまるごと落ちた場合は確かめていない。身元の根は、タスク定義を登録できる権限に依る（[4-2](#4-2-信頼できる範囲)）。
- **目的に対して:** ワークロードの身元を第三者が確かめる土台はできた。トークンを持ち主に暗号で結び付けること、人間の承認と AI の提案を区別して運ぶこと、監査に耐える記録は、まだない（[5 節](#5-目的に対してどこまで来たか)）。

## 1. 第三者による認証と監査の土台として、内部の mTLS を先に確かめた
目指しているのは、「AI による提案」と「人間による承認」を、当事者の自己申告ではなく第三者が認証でき、事後の監査にも耐えられるようにすることである。そのためには、まず「どのワークロードが呼んだか」を、呼んだ本人の申告ではなく、外の仕組みが確かめられる必要がある。この検証は、その土台として、token exchange とトークンの持ち主を結び付ける前の下準備に当たる。

前の試作 gekko_12 は、実行基盤を Lambda の Web Functions にした。ところが、関数にクライアント証明書が渡らず、SPIRE にも Lambda 向けの身元確認がなかった。そこで今回は、入口を作り込む前に、実行基盤が内部の mTLS を支えられるかを確かめた。費用の条件も重く、台を使わない間は費用をほぼ 0 にすることを前提にした。

## 2. 結論
### 2-1. 身元は、当事者の申告に依らず、AWS と ECS が付けた印で確かめられる
SPIRE は、台の身元を、EC2 のインスタンス識別ドキュメント（AWS が署名する）とタグで確かめた。タスクの身元は、ECS のエージェントが付けるコンテナのラベル（タスク定義のファミリーとコンテナ名）で確かめた。どちらも、呼ぶ側のアプリが自分で名乗る値ではない。登録したファミリーごとに別の SPIFFE ID が配られ、登録していないファミリーのタスクには配られなかった（findings [1-1](findings.md#1-1-docker-の-attestor-はecs-と同じ名前のラベルでファミリーごとに別の-spiffe-id-を配った)、[6-4](findings.md#6-4-aws_iid-のノードの確認はインスタンスのタグのセレクターで通った)、[7-1](findings.md#7-1-aws-でもシナリオは-1010-件が期待どおりだった)）。

### 2-2. 受け取る側は、mTLS の相手とトークンの呼び出し元を照合し、トークンの付け替えを拒める
受け取る側（ledger）は、mTLS の相手の SPIFFE ID に対応する client と、トークンの `client_id` と `act.client_id` の 3 つが一致したときだけ通した。乗っ取られた transfer が、BFF の交換したトークンを送ると拒まれ、乗っ取られた BFF が transfer を飛ばして直接呼ぶと拒まれた。本物の Cognito の token exchange（委任）のトークンでも、同じように働いた（findings [2-3](findings.md#2-3-受け取る側はspiffe-id-とトークンの呼び出し元が対応しないとき403-で拒んだ)、[7-2](findings.md#7-2-本物の委任のトークンはact-に-sub-と-client_id-の両方を持っていた)）。

### 2-3. 証明書の入れ替え、AZ、server の移動のどれでも、通信は切れない
有効期限 5 分の SVID を 30 分の間に十数回入れ替えても、連鎖の呼び出しは 1 件も失敗しなかった。2 つの AZ に複数のタスクを置き、Service Connect が両方の AZ に振り分けても、同じだった。SPIRE server を別の AZ へ移したときは、server が 24 秒いなかったが、通信は切れず、CA も変わらなかった（findings [7-3](findings.md#7-3-aws-でも30-分の連鎖の呼び出し-1404-回はsvid-の入れ替えを-1213-回挟んで失敗-0-件だった)、[7-5](findings.md#7-5-段-b-でも30-分の連鎖の呼び出し-1403-回は各タスクで-svid-の入れ替えを-13-回以上挟んで失敗-0-件だった)、[7-6](findings.md#7-6-spire-server-を別の-az-へ移すとserver-は-24-秒いなかったが連鎖の失敗は-0-件でca-も変わらなかった)）。

### 2-4. 台を 0 にすれば、残る費用は月 1 ドル未満の固定費だけになる（推定）
台はキャパシティプロバイダーが決め、タスクを 0 にすれば台も 0 になる（findings [6-1](findings.md#6-1-agent-の-daemon-だけが残った台をマネージドスケーリングは空として縮めた)）。台は公開 IPv4 も NAT も持たず、IPv6 だけで動いた（findings [5-4](findings.md#5-4-既定の-aws-の名前は-ipv4-だけでデュアルスタックの名前に向けると公開-ipv4-なしで動いた)）。台が 0 のときに残るのは、Cloud Map のホストゾーンとマネージドスケーリングのアラームの固定費と、EFS と ECR の保存の分である。単価は [runbook](runbook.md#aws-の費用の見込み) にある。

### 2-5. 採るときの条件
| 条件 | この作りで足りるか | 理由 |
|---|---|---|
| 台の数とタスクの数を、あとから増やす | 足りる | 台の数、タスクの数、AZ は、パラメーターだけで変わった（段 A → 段 B） |
| SPIRE server が計画して入れ替わる（更新、台の入れ替え） | 足りる | 24 秒で起き直し、SVID の有効期限（5 分）に収まった |
| AZ がまるごと落ちても止まらない | 分からない | 移し先に台がなければ、台を起こすところから始まる。5 分に収まるかは確かめていない |
| タスク定義を登録できる人が多い | 足りない | 登録できる者は、どのファミリーの身元も得られる（[4-2](#4-2-信頼できる範囲)） |

## 3. 身元は、台からトークンまで 1 本の鎖でつながっている
| 段 | 誰が確かめるか | 確かめるもの | 根拠 |
|---|---|---|---|
| 台 | SPIRE server | EC2 のインスタンス識別ドキュメントと、タグ `gekko13-role` | findings [6-4](findings.md#6-4-aws_iid-のノードの確認はインスタンスのタグのセレクターで通った) |
| タスク | SPIRE agent（docker の attestor） | ECS が付けるラベル（ファミリーとコンテナ名） | findings [1-1](findings.md#1-1-docker-の-attestor-はecs-と同じ名前のラベルでファミリーごとに別の-spiffe-id-を配った) |
| 通信の相手 | 呼ぶ側と受け取る側のアプリ | mTLS の証明書の SPIFFE ID | findings [2-1](findings.md#2-1-アプリが終える-mtls-は証明書なしとspire-以外の認証局の証明書をtls-で拒んだ)、[2-2](findings.md#2-2-呼ぶ側は相手の-spiffe-id-が違えば接続を止めた) |
| トークン | 受け取る側のアプリ | SPIFFE ID に対応する client と、`client_id`、`act.client_id` | findings [2-3](findings.md#2-3-受け取る側はspiffe-id-とトークンの呼び出し元が対応しないとき403-で拒んだ) |

この鎖のうち、トークンの段だけは、暗号ではなく対応表でつながっている。アプリの設定に「この SPIFFE ID には、この client」という表を持ち、照合している。なぜこの作りにしたかは [design-decisions](design-decisions.md) にある。

## 4. 予測と結果、信頼できる範囲
### 4-1. 事前の予測と結果
ケースと予測は [plan.md](plan.md) の 3 節と 4 節で、測る前に決めた。

| 予測 | ローカル | AWS 段 A | AWS 段 B |
|---|---|---|---|
| 1-a、1-b: 登録したファミリーだけに、別々の SPIFFE ID が配られる | 一致 | 一致 | 一致 |
| 2: 5 分の SVID で 30 分呼び続けて、失敗 0 件、入れ替え 10 回以上 | 一致 | 一致 | 一致（各タスク） |
| 3-a〜3-g: 正しい呼び出しは通り、6 つの攻撃は拒まれる | 一致 | 一致 | 一致 |
| B-1: 各サービスのタスクが、2 つの AZ に分かれる | — | — | 一致 |
| B-4: server を別の AZ へ移しても、CA は変わらず、失敗 0 件 | — | — | 一致 |

合格の基準 (a)〜(d) は、すべて満たした。1-c（ホストで `docker run` にラベルを偽る）は、予測どおり SVID が出た。合否には入れず、残るリスクとして扱う。

### 4-2. 信頼できる範囲
- **測れたこと:** 東京リージョンの 1 つと 2 つの AZ で、t4g.small の 2 台まで、各サービス 2 タスクまで。server の入れ替えは、計画して止め、移し先の AZ に台がすでにあった場合。
- **測れなかったこと:** AZ がまるごと落ちた場合、server のタスクや台が突然消えた場合、3 台以上と 3 タスク以上の場合。これらに結論は出さない（findings [8 節](findings.md#8-未確認)）。
- **推定:** AZ がまるごと落ちて、台を起こすところから始まると、server の起き直しが SVID の有効期限（5 分）を超えるおそれがある。台の起動とイメージの取得に、数分かかるため。
- **前提 1:** タスク定義をファミリーに登録できる者は、そのサービスの身元を得られる（findings [1-3](findings.md#1-3-ラベルを偽ったコンテナにも-svid-が出る)）。検証のプローブは、この性質をわざと使った。外れたときの影響: 登録の権限が広ければ、2-1 の「申告に依らない」は成り立たない。本番では、`ecs:RegisterTaskDefinition` とホストへのログインの権限を、身元の根として守る必要がある。
- **前提 2:** Cognito の委任のトークンの形（`act` に `sub` と `client_id`）は、2026-11 の実測である（findings [7-2](findings.md#7-2-本物の委任のトークンはact-に-sub-と-client_id-の両方を持っていた)）。外れたときの影響: 形が変われば、2-2 の照合のコードを直す。
- **前提 3:** AWS の API に IPv6 だけで届くのは、デュアルスタックの名前に向けた場合に限る（findings [5-4](findings.md#5-4-既定の-aws-の名前は-ipv4-だけでデュアルスタックの名前に向けると公開-ipv4-なしで動いた)）。外れたときの影響: 届かない API があれば、公開 IPv4 の費用が台ごとにかかる。

## 5. 目的に対して、どこまで来たか
**到達したこと:** 「どのワークロードが呼んだか」を、呼んだ本人の申告ではなく、第三者が確かめられるようになった。確かめる第三者は、AWS の識別ドキュメント、ECS のラベル、SPIRE の CA である。受け取る側は、その身元と、トークンが示す呼び出し元を照合できる。この土台は、台の数と AZ に依らず、使わない間はほぼ費用をかけずに保てる。

**まだ足りないこと:** 次の 4 つは、目的（第三者による認証と、事後の監査）に必要だが、この検証では作っていない。どれも、次の題材の論点として並べる。

| 論点 | 今の状態 | 足りないもの |
|---|---|---|
| (a) トークンと持ち主の結び付け | トークンは、持っていれば誰でも出せる（bearer）。持ち主は、受け取る側の対応表で照合している | トークンを、持ち主の鍵（SVID）に暗号で結び付けること。送り主に縛られたトークン（RFC 8705 の証明書に結び付いたトークンなど）が候補になる。Cognito が対応するかは未確認 |
| (b) 人間の承認と AI の提案の区別 | 利用者のトークン（人間）と、サービスの身元（ワークロード）はあるが、「AI のエージェントが提案した」「人間が承認した」を区別して運ぶ仕組みはない | AI のエージェントに身元を配ること、提案と承認を別々のトークンや主張として運ぶこと |
| (c) 監査に耐える記録 | アプリのログはあるが、誰が、何を、誰の権限で行ったかを、改ざんに耐える形で残していない | 呼び出しごとに、SPIFFE ID、トークンの主体と行為者（`act`）、操作を、後から検証できる形で残すこと |
| (d) 身元の根の守り | 身元の根は、タスク定義を登録できる権限に依る（前提 1） | 登録の権限を絞ること、登録そのものを記録して監査できるようにすること |
