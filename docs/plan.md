# AI の提案と人間の承認を、第三者が確かめられる形で、ECS の上で安く動かす（第 2 部の計画）

**この文書の読み手:** この検証の進め方と合格の基準を知りたい人、同じ検証を再現・拡張したい人。AWS と OAuth の基礎は知っているが、SPIFFE と SPIRE は知らないことがある。確かめた事実は [findings.md](findings.md)、進め方の記録は [log.md](log.md)、判断の理由は [design-decisions.md](design-decisions.md)。用語は [用語集](glossary.md)。

## 要旨
- **目指すこと:** 「AI による提案」と「人間による承認」を、当事者の自己申告に依らず第三者が認証でき、事後の監査に耐えるようにする。題材は、gekko_11 の年金保険の申込みの流れで、これを AWS の上で、使わない間はほぼ費用をかけずに動かす。
- **確かめること:** gekko_11 が k3d の上で満たした 12 の要件を、ECS on EC2 の基盤（IPv6 だけ、インスタンスを 0 にできる）の上でも満たせるか。
- **測り方:** 段 C で、基盤が違っても方式が成り立つかを 4 件で確かめる。段 D で、gekko_11 の 27 のシナリオを当てる（[3 節](#3-段-c-のケースと予測)、[4 節](#4-段-d-gekko_11-の流れを-ecs-に載せ27-のシナリオで手口が止まるかを見る)）。
- **測る前に決めること:** 予測と合格の基準（[5 節](#5-合格の基準)）。結果を見てから基準を変えない。
- **この文書に書かないこと:** 状況や費用の実績。[log.md](log.md) に書く。

## 1. 自己申告に依らない証拠を、安い基盤で作る
AI が代理として取引を進めるとき、AI の言い分のままでは、誰の依頼か、内容は依頼どおりか、権限の範囲内かを確かめられない。gekko_11 は、年金保険の申込みの流れで、これを確かめる仕組みを作った。確かめる根拠は、AI と独立した者の証明と署名である（gekko_11 の purpose の 3 章、architecture の 1-2 節の要件 1〜12）。この検証は、その仕組みを AWS の上で動かす。

これまでの試作は、それぞれ次のところで止まった。この検証の第 1 部は、ワークロードの身元と mTLS を、インスタンスの数と AZ に依らず安く作れることを確かめた。第 2 部は、その基盤の上に、gekko_11 の仕組みを載せる。

| 試作 | 基盤 | 解けたこと | 止まったところ |
|---|---|---|---|
| gekko_11 | k3d、Keycloak、Spring Authorization Server、Envoy、SPIRE | 12 の要件、27 のシナリオ | 手元のクラスタだけで、AWS では動かしていない |
| gekko_12 | Lambda、Cognito | 費用 | Lambda では mTLS が作れず、Cognito ではトークンを鍵やリクエストの中身に結び付けられない（gekko_12 の実測 1-7） |
| この検証の第 1 部 | ECS on EC2、SPIRE、IPv6 だけ | インスタンスの数と AZ に依らない mTLS。インスタンスが 0 なら固定費は月 1 ドル未満（推定） | トークンと持ち主の結び付け、承認の証拠、監査の記録は作っていない |

第 2 部の方式は、gekko_11 に従う。ログインサーバーと認可サーバーは、Keycloak と Spring Authorization Server にする。パスキーの RP ID は、CloudFront の既定のドメインにする（[design-decisions](design-decisions.md)）。

## 2. 3 段で確かめる
| 段 | 確かめること | 環境 |
|---|---|---|
| 段 C | gekko_11 の方式が、違う基盤（ECS の bridge モード、IPv6 だけ、CloudFront、AWS）でも成り立つか | AWS、1 つの AZ。部品ごとに小さく確かめる |

## 3. 段 C のケースと予測
| ケース | 狙い | 予測 | 外れたときの次の一手 |
|---|---|---|---|
| C-1 | CloudFront から、公開 IPv4 のないインスタンスの上のサービスに届くか | IPv6 の送り先か、VPC の中の送り先（VPC origin）のどちらかで届く（推定） | ロードバランサー（固定費）か、公開 IPv4（インスタンスごと 1 時間ごと）かを、持ち主と決める |
| C-2 | CloudFront の既定のドメインを RP ID にして、パスキーの登録と署名ができるか。ログインサーバーと顧客のアプリを、同じ名前の下にパスで振り分けられるか | できる。`cloudfront.net` が Public Suffix List にあるため（推定） | 独自のドメイン（登録の費用）を、持ち主と検討する |
| C-3 | Keycloak と Spring Authorization Server が、どの大きさのインスタンスで動き、インスタンスを起動してから使えるまで何分かかるか | t4g.medium 1 台に、2 つの JVM と SPIRE と既存のサービスが載る。インスタンスを起動してから使えるまで 10 分以内（推定） | インスタンスの大きさか、JVM の設定を見直す |
| C-4 | Envoy なしで、Java のサービスが SPIFFE の mTLS を自分で終えるか。Spring Authorization Server が、交換したトークンを、頼んだ者の SVID の証明書に結べるか（RFC 8705 の `cnf`） | java-spiffe などで終えられ、gekko_11 と同じ形のトークン（`act` と `cnf`）が出る | ECS の awsvpc でサイドカーを置く案を検討する（ENI の数の制約がある） |

## 4. 段 D: gekko_11 の流れを ECS に載せ、27 のシナリオで手口が止まるかを見る
段 D は、gekko_11 の 7 つのサービスを ECS のサービスにし、gekko_11 の 27 のシナリオを当てる。方式は gekko_11 に従い、変えるのは、基盤の違いで成り立たない 4 つの点だけにする（4-1）。作る順は D0、D1、D2 の 3 つに分け、段ごとに予測を置く（4-2、4-3）。D1 の前に、サービスを複数のタスクにする土台（共有の保存先）を作る（4-6）。各段の作業は、始める前に小さな計画にして、持ち主の承認を得る。

### 4-1. サービスはそのまま移し、確かめの場所、振り分け、記録、データの 4 点を替える
gekko_11 の 7 つのサービス（gekko_11 の architecture の 2-1 節）は、それぞれ ECS のサービスにする。コードは gekko_11 から写して手を入れる。替える 4 点と理由は、次のとおり。判断の行は [design-decisions](design-decisions.md) にある。

| 点 | gekko_11 | 段 D | 替える理由 |
|---|---|---|---|
| エンドポイントの確かめ | 各 Pod の Envoy と token-guard（gekko_11 の D-16） | アプリの中。TypeScript のサービスは token-guard をライブラリとして読み、Java の保険会社のシステムは servlet のフィルターと nimbus-jose-jwt（計画では Spring Security と書いた。design-decisions の判断 50）、Python の事務サービスは自前の確かめで、同じ判定をする | bridge モードでは、サイドカーの後ろのアプリにも直接届く |
| 入口の振り分け | 入口の Envoy が、名前で振り分ける（gekko_11 の D-25） | CloudFront から呼ぶ入口のリバースプロキシ（Lambda の Web Functions）が、パスで振り分ける。`/login` は Keycloak、`/audit` は監査の画面、それ以外は顧客のアプリ | パスキーの RP ID が、ディストリビューションのドメイン名 1 つしかない |
| 記録の集約 | Alloy と、名前空間ごとの Loki（gekko_11 の D-30） | CloudWatch Logs。書いた者は、ECS が付けるログストリームの名前で決める | 固定費のない、AWS の標準の仕組みで足りる |
| データ | 永続のボリューム | Aurora Serverless v2 に置き、全部のサービスで共有する。インスタンスを 0 にしても残る | サービスを複数のタスクにするには、共有の保存先が要る。持ち主の決定（4-6） |

サービスの言語は、エンタープライズで使われる 4 つの言語を、それぞれの得意な所に当てる（持ち主の決定）。監査サービスだけは、gekko_11 の Java から Go に書き直す。

| 言語 | サービス |
|---|---|
| TypeScript | 顧客のアプリ（画面と BFF）、営業 AI エージェント、入口のリバースプロキシ |
| Java | ログインサーバー（Keycloak）、認可サーバー（auth）、保険会社のシステム |
| Python | 事務サービス（MCP サーバー） |
| Go | 監査サービス |

サービスのトークンを受け取る確かめは、TypeScript、Java、Python の 3 つで書く。3 つが同じ判定をするよう、共通の試験の例で揃える（[design-decisions](design-decisions.md)）。営業 AI エージェントは、まず台本で動かし、主の流れが通ってから本物の Claude に替える。

### 4-2. 作る順は、基盤の作り替え、冗長化の土台、主の流れと 15 のシナリオ、残りの 12 のシナリオ
各段の結果と、今どの段にいるかは、[log.md の現在の状況](log.md#現在の状況2026-11-23)にある。この表は、測る前に決めた作る順で、結果を見てから書き換えない。

| 段 | 作ること | 確かめること |
|---|---|---|
| D0 | 内部向けの ALB と、それを指す VPC origin。ECS のスタックを基盤とアプリの 2 つに分ける。第 1 部のアプリ（bff、transfer、ledger、プローブ）を ECS から外す。edge-check は、2 つの AZ に届くかを確かめるエンドポイントとして残す | CloudFront から ALB を通して、2 つの AZ のどちらのインスタンスのタスクにも届く。インスタンスが 0 から使えるまでの時間 |
| D0-b | 入口を、ALB から Web Functions のリバースプロキシに替える（[design-decisions](design-decisions.md) の判断 31、32）。リバースプロキシは、名前空間の SRV で送り先を見つける。使わない間は、インスタンスとタスクを 0 にするだけにする | D0 と同じ。加えて、本文付きの POST がリバースプロキシを通って届くこと、リバースプロキシのエンドポイントを直接呼べないこと |
| D1-a1 | Aurora Serverless v2（PostgreSQL 17、最小 0 ACU）を作る。Keycloak、SPIRE server、auth の保存先を Aurora に移し、どれも 2 タスクにして 2 つの AZ に散らす。タスクの数を自動で増減させる（4-6） | インスタンス 1 台を止めても、入口と SVID が止まらない。インスタンスが 0 から使えるまでの時間（Aurora の再開を含む） |
| D1-a2 | 7 つのサービスを載せ、主の流れ（gekko_11 の architecture の 3 章の 7 段）を手口なしで通す。新しいサービスは 1 タスクで、状態をメモリに持つ。次の 3 つの小さな段で作る | ログインから照合まで、最後まで通る。監査の画面に、その契約の突き合わせが出る。台本で通したあと、本物の Claude に替えても通る |
| D1-a2-1 | Keycloak と auth を gekko_11 のログインサーバーと認可サーバーに替え、auth の状態を Aurora に移す。顧客のアプリを載せ、`/` を向ける | パスキーで登録とログインができ、顧客のアプリがトークンを受け取る |
| D1-a2-2 | 営業 AI エージェント（台本）、事務サービス、保険会社のシステムを載せる | 案の提示から照合まで（主の流れの 2〜7 段）が通る |
| D1-a2-3 | 監査サービス（Go）を載せ、`/audit` を向ける。記録は CloudWatch Logs から読む | 監査の画面に、その契約の突き合わせが出る |
| D1-a3 | D1-a2 で載せたサービスの状態を Aurora に移し、2 タスクにする。次の 3 つの小さな段で作り、最後に AWS でまとめて確かめる。タスクの数は、全部のサービスで 2 に固定する（判断 56） | インスタンス 1 台を止めても、主の流れが通る |
| D1-a3-1 | 保険会社のシステムの状態（nonce、契約、送り出し）を Aurora に移し、提示の鍵を共有する。事務サービスは 2 タスクにするだけにする（状態がない） | 同じ nonce の申込みを 2 つのタスクへ同時に送っても、通るのは 1 つ |
| D1-a3-2 | 顧客のアプリのセッション、ログインの途中の情報、受信箱と、監査サービスのセッションを Aurora に移す | どちらのタスクに当たっても、ログインしたままでいられる |
| D1-a3-3 | 営業 AI エージェントの会話を Aurora に置き、どのタスクでも次の回を続けられるようにする。台本で確かめる | 顧客の答えを待つ間に会話を始めたタスクが消えても、もう片方のタスクで会話が続く |
| D1-b | D1 の 15 のシナリオ（4-4） | 手口が止まる。止めた防御が、gekko_11 の scenarios の 3 章の「止める防御」に入っている |
| D2 | D2 の 12 のシナリオ（4-4） | D1-b と同じ |

edge-check と、第 1 部のアプリのファイル、Cognito のスタックは、D1-a2 の途中（2026-11-22）に消した（[log.md](log.md)）。

### 4-5. 作るときに見落としやすい点
- リバースプロキシの NetworkConnector は、2 つの AZ のサブネットに置く。インスタンスの ASG は、既定では 1 つの AZ に置いている（`GEKKO13_AZS=2` で 2 つ）。
- Web Functions は HTTP/1.1 だけで、WebSocket は使えない。Host がリバースプロキシのエンドポイントの名前でないと拒むので、CloudFront は Host を送らない。
- Keycloak、顧客のアプリ、監査の画面が同じオリジンになる。Cookie のパスと、リダイレクトの URI を分ける。
- メモリは、Java のサービス 3 つ、Keycloak、Node のサービス 3 つで約 2 GB と見込む（推定。findings 4-11 の値から見積もった）。インスタンスは 2 vCPU、4 GB 以上のスポットで、上限を 4 台にする。
- 記録の書いた者を偽る道を塞ぐ。タスクのロールに、ログを書く権限を与えない。インスタンスの認証情報を、コンテナに出さない（IMDS のホップを 1 のままにする）。
- ECS のテンプレートは、直接送れる大きさの上限に近い（[findings 4-12](findings.md#4-12-日本語のコメントを含めた-ecs-のテンプレートは直接送れる大きさ51200-バイトを超えた)）。サービスを足す前に、スタックを分ける。
- 署名鍵を起動ごとに作るサービス（auth、保険会社のシステム）は、複数のタスクで鍵がずれる。片方が出したトークンを、もう片方が確かめられない。鍵を共有する（gekko_11 の implementation の 5 節では、鍵を起動ごとに作っていた）。
- Keycloak の複数化には、タスクどうしのキャッシュの共有（JGroups）が要る。bridge のタスクは、相手に知らせる宛先（インスタンスの IP とインスタンスのポート）を自分で決められない。
- SPIRE server を 2 つにすると、server ごとに CA の鍵を持つ。agent が最初に信じるバンドル（今は EFS）に、両方が入るかを確かめる。
- Aurora のパスワードを Secrets Manager に置くと、月の固定費（1 つ月 0.4 ドル）がかかる。パスワードは SSM の SecureString に置き、ECS がタスクに渡す。Aurora はクライアントの証明書での認証に対応しないので、データベースへの通信は SVID の mTLS にできない（TLS とパスワードにする）。

### 4-6. 冗長化の土台は、Aurora Serverless v2 を全部のサービスで共有する
D1-a1 では、1 タスクのサービス（Keycloak、SPIRE server、auth）を、2 タスクにする。インスタンスはスポットで、中断されることがある。どれも状態を持つので、タスクの外に、共有の保存先が要る。保存先は、Aurora Serverless v2（PostgreSQL 17）を 1 つ置き、サービスごとにデータベースのロールを分ける。理由と退けた案（Aurora DSQL など）は、[design-decisions](design-decisions.md) にある。

| 部品 | 費用（東京） | いつかかるか |
|---|---|---|
| Aurora Serverless v2 の計算 | 1 ACU 時間 0.15 ドル。0.5〜1 ACU なら 1 時間 0.075〜0.15 ドル（推定） | 動かしている間。タスクが 0 になって 5 分で止まり、0 になる |
| Aurora の保存 | 1 GB 月 0.12 ドル | いつも |
| タスクのオートスケーリング | 1 つの方針でアラームが 2 つ（1 つ月 0.1 ドル） | いつも。D1-a3 で外し、性能を確かめるときに戻せる形で残す（判断 56） |

Aurora の計算の費用は、動かしている間、スポットのインスタンス 2 台（1 時間約 0.05 ドル）より高い。止めている間の費用は、ほぼ保存だけで変わらない。Aurora が止まっているときは、インスタンスを起動すると約 15 秒で再開する。この分が、インスタンスが 0 から使えるまでの時間に加わる。

D1-a1 は、当時の 3 つのサービス（Keycloak、auth、edge-check）と SPIRE server で確かめた。D1-a2 の 7 つのサービスは、同じ土台に載せる。

## 5. 合格の基準
- (a) 段 C の C-1〜C-4 がすべて予測どおりなら、段 D に進む。外れたものは、3 節の「次の一手」を持ち主と決めてから進む。

- (c) 段 D の D2 の 12 のシナリオでも、手口がすべて止まる。(b) と (c) を満たせば、gekko_11 の要件 1〜12 を AWS の上で満たしたとする。

## 6. 何を取るか
- シナリオごとの期待と実際の応答（gekko_11 と同じく、どの防御で止まったか）。
- 段 C の各ケースの結果（届いた経路、RP ID の扱い、インスタンスの大きさと起動の時間、トークンの形）。
- トークン（A、B、C）の形。値は伏せ、どの者を指すかだけを残す。
- 段 D の各段の結果（インスタンスが 0 から使えるまでの時間、主の流れが通ったか、シナリオごとに止めた防御）。D1-a1 では、インスタンス 1 台を止めたときの、失敗したリクエストの数と時間、Aurora が止まるまでと再開するまでの時間も取る。
- AWS の費用。インスタンスの時間、CloudFront の転送、リバースプロキシのリクエストと CPU とメモリ、Aurora の ACU 時間と保存、D0 の間の ALB の時間と LCU。
