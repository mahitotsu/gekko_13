# ECS on EC2 で、内部の通信を SPIFFE の mTLS で守れるかを確かめる（計画）

**この文書の読み手:** この検証の進め方と合格の基準を知りたい人、同じ検証を再現・拡張したい人。確かめた事実は [findings.md](findings.md)、進め方の記録は [log.md](log.md)、判断の理由は [design-decisions.md](design-decisions.md)。用語は [用語集](glossary.md)。

## 要旨
- **確かめること:** ECS on EC2 で、SPIRE がタスクごとに身元を配り、受け取る側が mTLS の相手とトークンの呼び出し元を照合できるか。台の数と AZ に依らずに成り立つか。
- **測り方:** BFF → transfer → ledger の 2 段の連鎖に、同じシナリオを当てる。動かす順は、ローカルの docker、AWS の段 A（1 AZ、各サービス 1 タスク）、段 B（2 AZ、各サービス 2 タスク）。
- **測る前に決めること:** 予測と合格の基準（[5 節](#5-合格の基準)）。結果を見てから基準を変えない。
- **この文書に書かないこと:** 状況や費用の実績。[log.md](log.md) に書く。

## 1. 先に内部の mTLS を確かめる
前の試作 gekko_12 は、入口（ログイン、パスキー、追加認証）を先に固めた。実行基盤は費用を 0 にできる Lambda の Web Functions にしたが、関数にクライアント証明書が渡らず、SPIRE にも Lambda 向けの身元確認がなかった。その結果、内部の mTLS が成り立たず、STS の署名を使った独自の送り主の証明を重ねることになった。

内部の mTLS ができるかは、実行基盤と費用の条件で最初に決まる。そこで、入口を作り込む前に、基盤が内部の mTLS を支えられるかを確かめる。確かめる問いは次の 3 つ。

1. ECS on EC2 で、SPIRE がタスクごとに別々の SPIFFE ID を配れるか。
2. SVID の有効期限を 300 秒にしても、自動の入れ替えで通信が失敗しないか。
3. 受け取る側で、相手の SPIFFE ID とトークンの `act.client_id` を照合し、トークンの付け替えを止められるか。

本番では、サービスのタスクは複数になり、AZ をまたぐ。そこで、3 つの問いが、台の数と配置に依らずに成り立つかも確かめる。

## 2. 3 段で確かめる
| 段 | 環境 | 確かめること |
|---|---|---|
| ローカル | docker（`local/up.sh`）。ノードは join_token、トークンは模擬の発行者 | 3 つの問いの仕組みが成り立つか |
| AWS の段 A | ECS on EC2。台はキャパシティプロバイダー（t4g.small、0〜2 台）が決める。1 AZ で、各サービス 1 タスク。IPv6 だけで、公開 IPv4 なし。ノードは aws_iid、トークンは Cognito | ECS のラベル、aws_iid、IPv6、Service Connect、本物の token exchange で、ローカルと同じ結果になるか |
| AWS の段 B | 段 A と同じ作りで、2 つの AZ に、各サービス 2 タスク | タスクが複数になり AZ をまたいでも、同じ結果になるか。SPIRE server が入れ替わっても、通信が続くか |

ローカルの各コンテナには、ECS のエージェントが付けるのと同じ名前のラベルを付ける。こうすると、SPIRE の登録を、ローカルと AWS で同じにできる。AWS の作りの理由は [design-decisions.md](design-decisions.md) にある。

## 3. ケースと予測
「盗まれた鍵」のケースは、そのサービスが乗っ取られ、SVID の鍵とそのサービスが受け取ったトークンを持たれた想定で作る。

| ケース | 狙い | 予測 |
|---|---|---|
| 1-a | 登録したタスクのファミリーごとに SVID が配られる | ファミリーごとに別の SPIFFE ID が出る |
| 1-b | 登録していないファミリーのタスク | 20 秒待っても SVID が出ない |
| 1-c | ホストで `docker run` にラベルを偽って付けたコンテナ | SVID が出る。ホストで docker を操作できる者は root と同じ、という残るリスクになる |
| 2 | 300 秒の SVID で 30 分、1 秒ごとに連鎖を呼ぶ | 失敗 0 件。各サービスの SVID が 10 回以上入れ替わる |
| 3-a | 正しい証明書と正しいトークン | 200 |
| 3-b | 証明書なしで ledger を呼ぶ | TLS で拒否 |
| 3-c | transfer の鍵で、BFF が交換したトークン（`act.client_id` が BFF）を ledger に送る | 403 |
| 3-d | BFF の鍵で ledger を直接呼ぶ（transfer を飛ばす） | 403 |
| 3-e | 別の信頼ドメインの証明書、同じ SPIFFE ID を名乗る別の認証局の証明書 | TLS で拒否 |
| 3-f | transfer の鍵で、トークンなし | 401 |
| 3-g | 呼ぶ側が transfer のつもりで ledger につなぐ | 呼ぶ側が接続を止める |

AWS では、「盗まれた鍵」を持つ側を、乗っ取られたタスクとして実際に動かす（プローブ）。プローブは、bff、transfer、ledger の本物のファミリーの別の版のタスクとして動く。自分が得た SVID だけを使い、Service Connect の中から攻撃する。1-b は、登録していないファミリーのタスク（rogue）が、自分に SVID が出るかを確かめる。

## 4. 段 B のケースと予測
段 B は、`GEKKO13_AZS=2`、`GEKKO13_TASKS=2`、`GEKKO13_MAX_HOSTS=4` で作る（[runbook.md](runbook.md)）。2 つの AZ に台を置き、bff、transfer、ledger は各 2 タスクにする。

| ケース | 狙い | 予測 |
|---|---|---|
| B-1 | 2 つの AZ の台に、各サービスのタスクが分かれて置かれる | どのサービスも、2 つのタスクが別々の AZ に置かれる |
| B-2 | 3 節の 1-a、1-b、3-a〜3-g を、段 B の配置で回す | 3 節の予測と同じ。プローブが置かれた台と AZ は問わない |
| B-3 | 3 節の 2（入れ替え）を、段 B の配置で回す | 失敗 0 件。各サービスの各タスクで、SVID が 10 回以上入れ替わる |
| B-4 | 連鎖を呼び続けながら、SPIRE server のタスクを止め、別の台（できれば別の AZ）で起き直させる | CA の識別子は変わらない。server が、既に配った SVID の有効期限（5 分）の中で起き直せば、連鎖の失敗は 0 件 |

## 5. 合格の基準
- (a) 1-a、1-b、2、3-a〜3-g のすべてが予測どおりになる。1-c は合否に入れず、残るリスクとして記録する。
- (b) (a) を、ローカルと AWS の両方で満たす。AWS は段 A で判定する。
- (c) どれかが AWS で満たせなければ、ECS on EC2 を採るのを見直す。次の候補は EKS で、コントロールプレーンの固定費がかかる。
- (d) 段 B の B-1〜B-4 がすべて予測どおりになる。B-4 が満たせなければ、SPIRE server の冗長化（共有の SQL。固定費がかかる）を持ち主と検討する。

## 6. 何を取るか
- シナリオごとの期待と実際の応答（`node scripts/scenarios.ts` が JSON に書く。AWS では `scripts/aws-collect.ts` が、プローブの 3 つの役と rogue の結果をまとめる）。
- 入れ替えの試験の成功と失敗の件数、各サービスの SVID の入れ替えの回数（`node scripts/soak.ts`。AWS の回数は、アプリのログの `svid_rotated` から数える）。
- AWS では、SPIRE の server と registrar のログ（CA の識別子、agent の身元の確認、登録）。
- AWS では、マネージドスケーリングの指標（`CapacityProviderReservation`）と、タスクの置かれた台と AZ。

## 7. 制約
- 月額の固定費がかかる部品は、採る前に持ち主に確かめる。EC2 は検証の間だけ動かす。
- 入口（CloudFront から BFF まで）、データベースへの経路、パスキーと追加認証は、この検証の範囲に入れない。
- この環境には `docker compose` がないので、ローカルの環境は `docker run` で立てる。
