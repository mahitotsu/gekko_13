# AI の提案と人間の承認を、第三者が確かめられる形で、ECS の上で安く動かす（第 2 部の計画）

**この文書の読み手:** この検証の進め方と合格の基準を知りたい人、同じ検証を再現・拡張したい人。AWS と OAuth の基礎は知っているが、SPIFFE と SPIRE は知らないことがある。確かめた事実は [findings.md](findings.md)、進め方の記録は [log.md](log.md)、判断の理由は [design-decisions.md](design-decisions.md)。用語は [用語集](glossary.md)。

## 要旨
- **目指すこと:** 「AI による提案」と「人間による承認」を、当事者の自己申告に依らず第三者が認証でき、事後の監査に耐えるようにする。題材は、gekko_11 の年金保険の申込みの流れで、これを AWS の上で、使わない間はほぼ費用をかけずに動かす。
- **確かめること:** gekko_11 が k3d の上で満たした 12 の要件を、ECS on EC2 の基盤（IPv6 だけ、台を 0 にできる）の上でも満たせるか。
- **測り方:** 段 C で、基盤が違っても方式が成り立つかを 4 件で確かめる。段 D で、gekko_11 の 27 のシナリオを当てる（[3 節](#3-段-c-のケースと予測)、[4 節](#4-段-d-のシナリオと合格の基準)）。
- **測る前に決めること:** 予測と合格の基準（[5 節](#5-合格の基準)）。結果を見てから基準を変えない。
- **この文書に書かないこと:** 状況や費用の実績。[log.md](log.md) に書く。

## 1. 自己申告に依らない証拠を、安い基盤で作る
AI が代理として取引を進めるとき、AI の言い分のままでは、誰の依頼か、内容は依頼どおりか、権限の範囲内かを確かめられない。gekko_11 は、年金保険の申込みの流れで、これを確かめる仕組みを作った。確かめる根拠は、AI と独立した者の証明と署名である（gekko_11 の purpose の 3 章、architecture の 1-2 節の要件 1〜12）。この検証は、その仕組みを AWS の上で動かす。

これまでの試作は、それぞれ次のところで止まった。この検証の第 1 部は、ワークロードの身元と mTLS を、台の数と AZ に依らず安く作れることを確かめた。第 2 部は、その基盤の上に、gekko_11 の仕組みを載せる。

| 試作 | 基盤 | 解けたこと | 止まったところ |
|---|---|---|---|
| gekko_11 | k3d、Keycloak、Spring Authorization Server、Envoy、SPIRE | 12 の要件、27 のシナリオ | 手元のクラスタだけで、AWS では動かしていない |
| gekko_12 | Lambda、Cognito | 費用 | Lambda では mTLS が作れず、Cognito ではトークンを鍵や要求の中身に結び付けられない（gekko_12 の実測 1-7） |
| この検証の第 1 部 | ECS on EC2、SPIRE、IPv6 だけ | 台の数と AZ に依らない mTLS。台が 0 なら固定費は月 1 ドル未満（推定） | トークンと持ち主の結び付け、承認の証拠、監査の記録は作っていない |

第 2 部の方式は、gekko_11 に従う。ログインサーバーと認可サーバーは、Keycloak と Spring Authorization Server にする。パスキーの RP ID は、CloudFront の既定のドメインにする（[design-decisions](design-decisions.md)）。

## 2. 3 段で確かめる
| 段 | 確かめること | 環境 |
|---|---|---|
| 段 C | gekko_11 の方式が、違う基盤（ECS の bridge モード、IPv6 だけ、CloudFront、AWS）でも成り立つか | AWS、1 つの AZ。部品ごとに小さく確かめる |
| 段 D | gekko_11 の流れを動かし、27 のシナリオで、防御が手口を止めるか | AWS、1 つの AZ。D1 と D2 に分けて作る |
| 段 E | 2 つの AZ に複数のタスクを置いたときと、防御を外した複製（vulnerable）との比べ | 後回し。段 D のあとで、改めて計画する |

段 C は、判断を誤ると段 D がやり直しになる点を、作り込む前に確かめる。段 D は、防御がある状態で、手口を止めるかで判定する。防御を外したときに被害が出ることを見せるのは、段 E に回す。

## 3. 段 C のケースと予測
| ケース | 狙い | 予測 | 外れたときの次の一手 |
|---|---|---|---|
| C-1 | CloudFront から、公開 IPv4 のない台の上のサービスに届くか | IPv6 の送り先か、VPC の中の送り先（VPC origin）のどちらかで届く（推定） | ロードバランサー（固定費）か、公開 IPv4（台ごと 1 時間ごと）かを、持ち主と決める |
| C-2 | CloudFront の既定のドメインを RP ID にして、パスキーの登録と署名ができるか。ログインサーバーと顧客のアプリを、同じ名前の下にパスで振り分けられるか | できる。`cloudfront.net` が Public Suffix List にあるため（推定） | 独自のドメイン（登録の費用）を、持ち主と検討する |
| C-3 | Keycloak と Spring Authorization Server が、どの大きさの台で動き、台を起こしてから使えるまで何分かかるか | t4g.medium 1 台に、2 つの JVM と SPIRE と既存のサービスが載る。台を起こしてから使えるまで 10 分以内（推定） | 台の大きさか、JVM の設定を見直す |
| C-4 | Envoy なしで、Java のサービスが SPIFFE の mTLS を自分で終えるか。Spring Authorization Server が、交換したトークンを、頼んだ者の SVID の証明書に結べるか（RFC 8705 の `cnf`） | java-spiffe などで終えられ、gekko_11 と同じ形のトークン（`act` と `cnf`）が出る | ECS の awsvpc でサイドカーを置く案を検討する（ENI の数の制約がある） |

## 4. 段 D のシナリオと合格の基準
段 D のシナリオは、gekko_11 の 27 のシナリオ（gekko_11 の scenarios の 3 章）と同じ番号を使う。gekko_11 の要件 1〜12 の合格の基準は、どれもこのシナリオで判定する（gekko_11 の architecture の 1-2 節）。作る順は、D1 と D2 に分ける。

| 区分 | シナリオ | 選んだ理由 |
|---|---|---|
| D1 の前提 | 主の流れ（gekko_11 の architecture の 3 章の 7 段）を、手口なしで最後まで通す | 署名された案の提示、意向確認と申込みの署名、交換、検証と記録、直送、照合が、AWS の上でつながること |
| D1 | 1、7、8、9、10、11、12、14、16、18、19、20、22、23、25 | gekko_11 の 4 つのまとまりを、少なくとも 1 つずつ確かめる。証明（1、14、16、18、20、22、23、25）、署名（7、8、9）、受け付けと記録の規則（10、11、12）、事後の経路（19）。AWS で新しく作る点（トークンを SVID の証明書に結ぶ 22、23、経由を積む 20）を優先した |
| D2 | 2、3、4、5、6、13、15、17、21、24、26、27 | 残りのシナリオ |

## 5. 合格の基準
- (a) 段 C の C-1〜C-4 がすべて予測どおりなら、段 D に進む。外れたものは、3 節の「次の一手」を持ち主と決めてから進む。
- (b) 段 D の主の流れが最後まで通り、D1 の 15 のシナリオで、手口がすべて止まる。
- (c) 段 D の D2 の 12 のシナリオでも、手口がすべて止まる。(b) と (c) を満たせば、gekko_11 の要件 1〜12 を AWS の上で満たしたとする。
- (d) (b) か (c) が満たせないときは、どの防御が AWS の基盤で成り立たないかを記録し、方式を見直す。

## 6. 何を取るか
- シナリオごとの期待と実際の応答（gekko_11 と同じく、どの防御で止まったか）。
- 段 C の各ケースの結果（届いた経路、RP ID の扱い、台の大きさと起動の時間、トークンの形）。
- トークン（A、B、C）の形。値は伏せ、どの者を指すかだけを残す。
- AWS の費用（台の時間、CloudFront の転送）。

## 7. 制約と、第 2 部の完成
- 月額の固定費がかかる部品は、採る前に持ち主に確かめる。AWS に資源を作る前にも確かめる。台は検証の間だけ動かす。
- 営業 AI エージェントは、試験では台本で動かす。本物の Claude を使うかは、段 D の中で、費用と、IPv6 だけで API に届くかを確かめてから決める。
- 記録の保存の期間は、パラメーターで変えられるようにする。デモなので、長くは残さない。
- 第 2 部は、(b) と (c) を満たし、結論の報告書を書いたときに完成とする。完成したら、第 1 部の文書（`docs/phase1/`）と、第 2 部に引き継がなかったコードを消す。消す前に、対象を一覧で見せて、持ち主の承認を得る。
