## 現在の状況（2026-11-21）
- 第 2 部を始めた。題材は、gekko_11 の年金保険の申込みの流れで、これを第 1 部の基盤（ECS on EC2、SPIRE、IPv6 だけ）の上で動かす。
- 第 2 部の計画（[plan.md](plan.md)）を書いた。段 C の C-1 は予測どおりだった。CloudFront から、IPv6 だけのインスタンスの上のサービスに届いた（[findings 4-1](findings.md#4-1-cloudfront-は送り先の-ip-の種類を-ipv6-にするとipv6-だけのインスタンスに届いた既定の-ipv4-では届かなかった)）。
- C-4 も予測どおりだった。Spring Authorization Server は、Envoy なしで SVID の mTLS を終えた。交換したトークンは、呼び手の SVID の証明書に結ばれた（[findings 4-4](findings.md#4-4-spring-authorization-server-はenvoy-なしで-svid-の-mtls-を自分で終え交換したトークンを呼び手の-svid-の証明書に結んだ)）。
- C-2 と C-1b も予測どおりだった。入口を VPC origin に替え、インスタンスをプライベートのサブネットに移した（[findings 4-8](findings.md#4-8-cloudfront-はプライベートのサブネットのインスタンスに-vpc-origin-で届きパスで-2-つのエンドポイントに振り分けたインスタンスから見た送り主はcloudfront-の公開-ipv4-だった)）。ディストリビューションのドメイン名を RP ID にして、パスキーの登録と署名ができた（[4-10](findings.md#4-10-ディストリビューションの既定のドメインを-rp-id-にしてパスキーを登録し別のパスのエンドポイントで文書のハッシュに署名できたcloudfrontnet-は-rp-id-にできなかった)）。
- C-3 も予測どおりだった。t4g.medium 1 台に全部が載り、インスタンスが 0 の状態から約 6〜7 分で使えた（[findings 4-11](findings.md#4-11-t4gmedium-1-台に-keycloak-と認可サーバーが載りインスタンスが-0-の状態から約-67-分で使えたいちばん長いのは-vpc-origin-の向け直しだった)）。段 C の 4 件がすべて予測どおりなので、合格の基準 (a) を満たし、段 D に進める。
- 段 D の計画を書いた（[plan.md の 4 節](plan.md#4-段-d-gekko_11-の流れを-ecs-に載せ27-のシナリオで手口が止まるかを見る)）。
- D0 は予測どおりだった。入口を内部向けの ALB にし、インスタンスが 0 の状態から約 3 分で使え、2 つの AZ のどちらのインスタンスにも届いた（[findings 4-15](findings.md#4-15-入口を内部向けの-alb-にするとインスタンスが-0-の状態から約-3-分で使え2-つの-az-のどちらのインスタンスにも届いた)）。
- D0-b の作りを AWS に送った。入口のリバースプロキシ（Web Functions）は、名前空間の SRV で 2 つの AZ のタスクに届いた。本文付きの POST と Cookie も通った（[findings 4-17](findings.md#4-17-入口のリバースプロキシweb-functionsはnetworkconnector-の先から名前空間の-srv-を引き2-つの-az-のタスクに届いた本文付きの-post-と複数の-set-cookie-が通りエンドポイントを直接呼ぶと-403-だった)）。D0-b の「インスタンスが 0 から使えるまで」は、3 回とも 300 秒以内で、毎回 2 つの AZ が現れた。予測どおり（[findings 4-21](findings.md#4-21-入口を-web-functions-のリバースプロキシにしてもインスタンスが-0-の状態から約-34-分で使え2-つの-az-のどちらのインスタンスにも届いたインスタンスが-0-の間ディストリビューションは-503-を返した)）。次は、持ち主がパスキーを試す。そのあと D1-a1（冗長化の土台）、D1-a2（7 つのサービスと主の流れ）の順に進める（[plan.md の 4-2](plan.md#4-2-作る順は基盤の作り替え冗長化の土台主の流れと-15-のシナリオ残りの-12-のシナリオ)）。
- D1-a1 の 6 つの予測を確かめ、どれも予測どおりだった（[findings 4-26〜4-31](findings.md#4-31-aurora-と冗長化を足してもインスタンスが-0-の状態から約-3-分半4-分で使えたaurora-はつながりがなくなって-5-分ほどで一時停止し再開は-5-秒ほどだった)）。予測 5（auth の鍵の共有）は、鍵の形まで確かめた。トークンを出して別のタスクで確かめるのは、D1-a2 で行う。次は D1-a2 で、ログイン（D1-a2-1）、案の提示から照合まで（D1-a2-2）、監査（D1-a2-3）の順に作る（[plan.md の 4-2](plan.md#4-2-作る順は基盤の作り替え冗長化の土台主の流れと-15-のシナリオ残りの-12-のシナリオ)）。
- インスタンスは 0 にしてある。インスタンスは全部スポットで起動する。戻すときは `aws/scale.sh up`、使わない間は `aws/scale.sh down` で 0 にする。Aurora は、つながりがなくなって 5 分ほどで一時停止する。
