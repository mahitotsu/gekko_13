## 決めたこと
- 2026-11-15: ローカルの環境を、`docker compose` ではなく `docker run` で立てる。この環境に compose がなく、ECS も compose を使わないため。持ち主が承認した。
- 2026-11-15: Dockerfile から `RUN` をなくし、依存はホストで入れて写す。arm64 のエミュレーションがないため（[findings 4-4](findings.md#4-4-run-のない-dockerfile-ならエミュレーションなしで-arm64-のイメージを作れた)）。
- 2026-11-15: トークンの照合のコードは、gekko_12 の実測に合わせて `act.client_id` を見る。ドキュメントの例とは食い違うので、AWS の段で決め直す（[findings 4-2](findings.md#4-2-委任のトークンの形はドキュメントの例と-gekko_12-の実測で食い違う)）。
- 2026-11-15: 入れ替えの試験の予測「各サービスで 10 回以上入れ替わる」は、試験を回している間に、結果を見る前に計画へ書き足した。300 秒の SVID が半分の時間で入れ替わるという見込みから出した。
- 2026-11-15: シナリオ 1-c（ホストで `docker run`）は、AWS では行わない。ホストのシェルが要るため。合否の基準にはもともと入れていない。
- 2026-11-16: 持ち主が AWS に資源を作るのを承認した。
- 2026-11-16: ECS の作りを、スケールアウトしても壊れない形に直す。持ち主の指摘による。今の作りは、サービス間の呼び出し、agent から server への接続、SPIRE server の状態、登録の手順が、1 台を前提にしている。直し方は次の 4 つで、持ち主が承認した。
  - キャパシティプロバイダー（マネージドスケーリング）
  - アプリどうしの Service Connect（TCP の中継だけ）
  - Cloud Map の DNS で見つける、awsvpc の SPIRE server
  - EFS に置く、server の状態

  設計の判断は、作り終えてから [design-decisions.md](design-decisions.md) に書く。
- 2026-11-16: 持ち主が、月に約 0.7 ドルの固定費を承認した（推定。Cloud Map のホストゾーンが 0.5 ドル、マネージドスケーリングのアラーム 2 つが約 0.2 ドル、EFS はほぼ 0）。
- 2026-11-16: AWS の段を 2 つに分ける。段 A は 1 AZ で、各サービス 1 タスク。段 B はマルチ AZ で、複数タスクのサービス。段 B の確かめる項目と合格の基準は、結果を見る前に [plan.md](plan.md) に足す。
- 2026-11-16: CloudFormation のテンプレートの説明と Metadata は、英語で書く（[findings 5-1](findings.md#5-1-cloudformation-はテンプレートの-ascii-以外の文字をに置き換えた)）。
- 2026-11-16: この環境に cfn-lint が入っていなかったので、テンプレートの検査は `aws cloudformation validate-template` で行った。
- 2026-11-16: 段 A でも公開 IPv4 を付けず、IPv6 だけで動かす。持ち主の判断。
- 2026-11-16: アプリどうしの呼び出しに Service Connect を使う（TCP の中継だけ。Service Connect の TLS は使わない）。持ち主が承認した。
- 2026-11-16: プローブは、本物のファミリーの別の版のタスク定義で動く「乗っ取られたタスク」にする。台の数と配置に依らないため。findings 1-3 の残るリスクを、検証のためにわざと使う。持ち主が承認した。
- 2026-11-17: `aws/scale.sh down` は、タスクが 0 になったら ASG の希望台数を直接 0 にする。マネージドスケーリングの縮小の 15 分の待ちを省くため。持ち主が承認した。
- 2026-11-17: AWS の入れ替えの試験（シナリオ 2）は、持ち主の判断で翌日以降に回す。合格の基準 (b) は変えず、未判定とする。
- 2026-11-17: plan.md に、段 B のケース（B-1〜B-4）、予測、合格の基準 (d) を足した。段 B の結果はまだなく、結果を見る前に決めた。B-4（server の入れ替え）は、findings 6-5 の残るリスクを確かめるために足した。基準 (a)〜(c) は変えていない。(b) の AWS は、段 A で判定すると書き添えた。
- 2026-11-17: plan.md の AWS の段の環境の書き方を、今の作り（キャパシティプロバイダー、段 A と段 B）に合わせた。AWS で取るものから、`agent list` と `entry show` を外した。ホストに入らない作りにしたため、代わりに server と registrar のログを取る。
- 2026-11-17: design-decisions、runbook、glossary、CLAUDE.md を、今の作りに合わせて直した。
- 2026-11-17: SPIRE server の冗長化について、持ち主と次のとおり整理した（[findings 6-6](findings.md#6-6-spire-server-を冗長にするには全部の-server-が-1-つの-sql-のデータストアを共有するdynamodb-は使えない)、[6-7](findings.md#6-7-aurora-serverless-v2-は-0-acu-まで縮みつながりが-1-本でもあると止まらない)）。DynamoDB は SPIRE が対応しない。RDB を 1 つ共有するだけでは、可用性は server 1 つと変わらない。ECS の上の PostgreSQL は、止まると全体が止まる場所を移すだけ。server は 1 つのまま、冗長にするかとアプリのデータベースは、段 B の B-4 の結果を見て一緒に決める（design-decisions に「提案」として書いた）。

- 2026-11-18: B-4 の試験の長さを、移す前 3 分、全体 12 分にした。持ち主が承認した。plan.md の B-4 には長さの決まりがないので、基準の変更ではない。移したあとに 9 分見るので、SVID の有効期限（5 分）を超えて持ちこたえるかは判定できる。
- 2026-11-18: SPIRE server は 1 つのまま、止まったら速く起き直すことで耐える。B-4 の結果を見て、持ち主が承認した（design-decisions の状態を「提案」から「承認」にした）。確かめたのは計画した入れ替えだけなので、AZ がまるごと落ちた場合の扱いは、アプリのデータベースを決めるときに見直す。
- 2026-11-18: `aws/deploy.sh` は、ECS のスタックを更新する前に、spire-server のタスク数を 1 に戻す。`scale.sh down` のあとに更新すると、server のいないサービスが安定しないまま更新が待ち続けるため。
